\section{Why Reservation TTL Exists}
Atomic creation prevents immediate overselling, but a reservation that never
confirms must not hold finite resources forever. New bookings therefore store
\code{status = RESERVED} and a configurable \code{expires\_at} (ten minutes by
default). TTL separates a short reservation transaction from later confirmation
and bounds abandoned capacity.

\section{Expiry Worker}
The worker wakes every 30 seconds by default, prevents overlapping ticks in one
process, requests a default batch of 100, and delegates one transactional batch
to the lifecycle service. The service clamps externally supplied batch sizes to
1--500. Figure~\ref{fig:expiry-worker-sequence} shows the implemented flow.

\section{Scalable Worker Claiming}
\begin{lstlisting}[language=SQL,caption={Disjoint batch claim for expired reservations}]
SELECT id
FROM bookings
WHERE status = 'RESERVED'
  AND expires_at <= NOW()
ORDER BY expires_at, id
LIMIT :safe_limit
FOR UPDATE SKIP LOCKED;
\end{lstlisting}

Multiple workers claim disjoint rows without a distributed lock. Each claim
lock is held until the conditional status update, ticket restoration, reserved
voucher release, and audit insert commit. A repeat run cannot find the row as
\code{RESERVED} and therefore cannot release resources twice.

\section{Confirm-vs-Expire Race}
\begin{lstlisting}[language=SQL,caption={Conditional confirmation}]
UPDATE bookings
SET status = 'CONFIRMED', updated_at = NOW()
WHERE id = :booking_id
  AND status = 'RESERVED'
  AND expires_at > NOW();
\end{lstlisting}

The expiry and confirmation paths both require \code{status = RESERVED}; the
database row update is the arbitration point. The expiry/time predicate is
evaluated after any lock wait, so stale application time cannot confirm an
already-expired reservation. \code{CONC-004} proves one terminal outcome and a
resource state consistent with that winner.
