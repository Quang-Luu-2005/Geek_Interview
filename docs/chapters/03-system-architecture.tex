\section{Architecture Goals}
The architecture must keep correctness-sensitive transactions short and
understandable, preserve strong consistency for finite resources, support the
stated workload without speculative infrastructure, remain maintainable and
testable, reproduce locally, and expose explicit evolution seams.

\section{Selected Architecture: Modular Monolith and PostgreSQL}
\begin{decisionbox}[Use a modular monolith for the assessment]
Booking, inventory, voucher, and idempotency require strong transactional
coordination. Keeping these modules in one deployable process and one database
avoids distributed transactions while retaining explicit domain boundaries.
The stateless API can still be replicated horizontally when measured demand
requires it.
\end{decisionbox}

This selection is proportional to the stated 5--8.3 booking requests per
second. Microservices would add network failure modes, service discovery,
cross-service retry semantics, and distributed coordination without improving
the finite-resource guarantees demonstrated by this submission.

\section{Why PostgreSQL Is the Consistency Boundary}
Ticket inventory, voucher quota, booking state, audit history, and idempotency
records are relational and participate in the same business outcomes.
PostgreSQL conditional writes, row locks, constraints, and ACID rollback make it
the natural arbiter. Redis may later support a shared limiter/cache, but it is
not authoritative inventory and no Redis lock is needed for correctness.

\section{Scaling Direction}
Scale stateless API replicas first only after measuring database contention.
Multiple expiry workers already coordinate through \code{FOR UPDATE SKIP
LOCKED}. If post-commit integrations grow, a transactional outbox can bridge
database state to a broker without dual writes. Hot categories may ultimately
need admission control, queueing, or inventory partitioning, but those are
revisit decisions based on observed lock waits rather than baseline
requirements.
