\section{Known Limitations}
The current identity header is an assessment mechanism rather than production
authentication. Confirmation does not prove payment, inventory is not
seat-specific, and the process-local limiter/metrics need shared infrastructure
for multiple API replicas. The polling expiry worker provides bounded rather
than instantaneous expiry. Detailed assumptions remain in
\nolinkurl{docs/ASSUMPTIONS_SCOPE_LIMITATIONS.md}.

These limitations do not weaken the submitted guarantees: inventory cannot
oversell, one idempotent intent cannot double-book, voucher quota cannot
over-redeem, and competing terminal transitions cannot release resources twice.

\section{Payment Processing Scope}
Real payment processing is outside the assessment scope. The implementation
provides payment-adjacent behavior: a time-limited \code{RESERVED} booking,
immutable totals, conditional \code{RESERVED -> CONFIRMED}, cancellation or
expiry, exactly-once resource release, and retry-safe booking creation.

There is no provider client, payment session, authorization/capture, webhook
verification, payment-state table, settlement, refund, chargeback, or
reconciliation. A future flow is deliberately separated from the current
transaction:

\begin{center}
\small
\code{Reserve + commit RESERVED} $\rightarrow$
\code{External gateway} $\rightarrow$
\code{Verified webhook} $\rightarrow$
\code{New transaction} $\rightarrow$
\code{Conditional confirm}
\end{center}

\begin{decisionbox}[External-call boundary]
Never keep the booking/inventory transaction open while calling an external
payment provider. Provider interaction occurs after commit; its verified result
is handled idempotently in a new transaction and cannot overwrite an already
expired or cancelled booking.
\end{decisionbox}
