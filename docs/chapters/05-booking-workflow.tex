\section{Create Booking Sequence}
The create-booking use case converts one authenticated customer intent into one
replayable result. The full vector sequence diagram is supplied separately at
\nolinkurl{docs/figures/booking-sequence.pdf}, with editable source at
\nolinkurl{docs/diagrams/booking-sequence.mmd}. It is not embedded here because
its replay, conflict, sold-out, voucher, and rollback branches become too small
at normal report zoom. The same flow is captured compactly below.

The implemented sequence is:
\begin{enumerate}
  \item authenticate the assessment identity, validate the DTO, normalize items, and calculate a canonical request fingerprint;
  \item inspect an already-completed idempotency record for an immediate replay/conflict path;
  \item for a new logical request, begin one database transaction and claim the user, key, and fingerprint;
  \item validate that the concert and categories are bookable;
  \item reserve every category by atomic conditional update in deterministic order;
  \item validate and reserve voucher policy/quota when supplied;
  \item calculate subtotal, discount, and final amount from persisted server data;
  \item insert the booking, immutable items, initial status history, and completed idempotency response;
  \item commit and return the result.
\end{enumerate}

\section{Transaction Boundary}
The idempotency claim/completion, ticket reservation, optional voucher quota and
redemption, price snapshots, booking/items, and initial audit history share one
transaction. A failure in any dependent operation rolls all of them back. This
avoids a completed idempotency record for a booking that never committed and
avoids inventory or voucher leakage after later validation fails.

External calls such as email, analytics, or a future payment provider must not
extend this database transaction. They occur only after commit or through a
reliable post-commit pattern such as the optional transactional outbox.

\section{Multi-Category Reservation}
Category identifiers are normalized and processed in deterministic order. The
consistent lock/update order reduces deadlock risk, while one transaction makes
the request all-or-nothing: failure to reserve any category automatically
rolls back every earlier category and optional voucher write.
