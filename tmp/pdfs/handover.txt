Đọc sát đề bài cho thấy reviewer không yêu cầu một hệ thống production-ready, mà muốn đánh giá
ba thứ: cách bạn tư duy về backend design, cách tổ chức codebase, và cách reasoning về các issue/
workflow có thể xảy ra. Đề cũng yêu cầu toàn bộ kết quả được gom vào một folder/link để submit. Ở
phần deliverables, đề nêu trực tiếp: tài liệu System/Database Design có phân tích và giải thích, source
code, coding guideline/convention, hướng dẫn setup local, API documentation như Swagger, API
testing collection như Postman chạy được với local setup, và tài liệu assumptions / implemented scope /
not implemented / limitations. fileciteturn0file0

OpenAPI là lựa chọn phù hợp để biến API contract thành artifact machine-readable: OAS hiện định
nghĩa một interface description độc lập ngôn ngữ cho HTTP API và có thể được dùng bởi
documentation, testing và code-generation tools. Phiên bản chính thức hiện hành của specification là
OpenAPI 3.2.0; tuy nhiên nếu framework Swagger của bạn hỗ trợ 3.0/3.1 tốt hơn thì tool compatibility
quan trọng hơn việc cố dùng specification mới nhất. 1


Đối với visual documentation, Mermaid là lựa chọn rất hợp repository vì ERD, sequence diagram và
state diagram đều có syntax chính thức và có thể version-control cùng code. Mermaid cũng có
 timeline , nhưng tài liệu hiện ghi timeline vẫn là experimental diagram; vì vậy timeline chỉ nên là
asset phụ, còn booking race nên ưu tiên sequence diagram nếu bạn muốn stability tốt hơn.      2




Nguyên tắc cuối cùng: một reviewer nên clone repo, đọc README trong vài phút, chạy một command
để dựng môi trường, gọi được booking API, chạy test và nhìn thấy bằng chứng rằng inventory không
oversell.

Template one-page executive summary

docs/EXECUTIVE_SUMMARY.md nên ngắn đến mức reviewer đọc một lần là biết toàn bộ solution:



  # Executive Summary

  ## Problem

  This project implements the backend of a concert ticket booking platform
  supporting customer booking flows and internal operation workflows.

  The main engineering risks addressed are:
  - ticket overselling
  - duplicate booking caused by retries




                                                7
- voucher quota abuse
- temporary reservations
- flash-sale contention


Expected traffic from the assessment:
- ~50,000 users
- ~300–500 booking requests/minute

## Scope

Implemented:
- concert and ticket-category query
- ticket availability
- booking reservation
- voucher application
- idempotent booking creation
- booking lifecycle
- reservation expiration
- operator booking inspection/status updates

Not implemented:
- real payment gateway
- seat-level assignment
- refund workflow
- notification delivery
- multi-region deployment

## Architecture

Modular monolith + PostgreSQL.

PostgreSQL is the consistency boundary for:
- inventory
- booking
- voucher quota
- idempotency

Critical booking mutations execute in a single database transaction.

[Architecture diagram]

## Correctness Guarantees

1. Inventory never becomes negative.
2. One idempotency key creates at most one logical booking.
3. Voucher quota cannot exceed its configured limit.
4. Failed booking transactions do not consume inventory/vouchers.
5. Expired reservations release reserved resources.
6. Invalid booking-state transitions are rejected.

## Key Decisions




                                        8
  | Decision | Rationale |
  |---|---|
  | Modular monolith | Simple deployment and ACID transaction boundary |
  | PostgreSQL | Strong consistency around finite resources |
  | Conditional UPDATE | Prevent overselling without read-then-write race |
  | Idempotency key | Retry-safe POST /bookings |
  | Background expiry worker | Release abandoned reservations |

  - p99 latency: ___

  See README.md for:
  - migrations and seed
  - tests
  - Swagger
  - Postman
  - concurrency/load tests

  [3–5 concise items]

DATABASE_DESIGN.md

Purpose: chứng minh correctness được đặt xuống database thay vì chỉ phụ thuộc vào if trong
application.


PostgreSQL hiện hỗ trợ CHECK , UNIQUE , primary/foreign-key constraints; unique constraint trên
nhiều columns bảo đảm tính duy nhất của tổ hợp giá trị và PostgreSQL tự tạo unique B-tree index cho
unique constraint. Đây là nền tảng phù hợp cho idempotency uniqueness và per-user voucher
redemption. 6

  ADD CONSTRAINT ck_inventory_non_negative
  CHECK (available_quantity >= 0);

  ALTER TABLE ticket_inventories
  ADD CONSTRAINT ck_inventory_not_above_total
  CHECK (available_quantity <= total_quantity);

  ALTER TABLE idempotency_records
  ADD CONSTRAINT uq_idempotency_user_key
  UNIQUE (user_id, idempotency_key);

  ALTER TABLE voucher_redemptions
  ADD CONSTRAINT uq_voucher_redemption_user
  UNIQUE (voucher_id, user_id);


CHECK phù hợp với invariant của chính row như available_quantity >= 0 ; PostgreSQL lưu ý
không nên dùng CHECK để enforce invariant phụ thuộc dữ liệu row khác/table khác, mà nên dùng các
constraint phù hợp như UNIQUE , FOREIGN KEY hoặc cơ chế transactional khác.     6




Atomic inventory update:



  UPDATE ticket_inventories
  SET available_quantity = available_quantity - :quantity
  WHERE ticket_category_id = :ticket_category_id




                                               14
    AND available_quantity >= :quantity
  RETURNING ticket_category_id, available_quantity;


Interpretation:



  1 returned row → reservation succeeded
  0 returned rows → insufficient inventory / no matching inventory


PostgreSQL UPDATE supports a conditional WHERE clause and RETURNING , nên application có thể
phân biệt thành công/thất bại dựa trên row thực sự được update thay vì làm unsafe
 SELECT → check → UPDATE . 8


Atomic voucher quota update:



  UPDATE vouchers
  SET used_count = used_count + 1
  WHERE id = :voucher_id
    AND status = 'ACTIVE'
    AND starts_at <= NOW()
    AND expires_at > NOW()
    AND used_count < usage_limit
  RETURNING id, used_count;


Voucher eligibility khác như applicable concert/category có thể validate trước hoặc kết hợp trong query;
điểm cốt lõi là quota mutation phải conditional tại DB.


Transaction skeleton:



  BEGIN;

  -- reserve inventory atomically
  -- reserve voucher quota atomically
  -- create booking
  -- create booking items
  -- create voucher redemption

  COMMIT;


Nếu booking gồm nhiều category, document rằng application xử lý category IDs theo deterministic
order để giảm nguy cơ deadlock; PostgreSQL documentation cũng chỉ ra ordering các rows trong batch
update có thể giúp tránh deadlock khi concurrent commands dùng cùng ordering. 8


Expiry worker plus point:



  SELECT id
  FROM bookings




                                                  15
  WHERE status = 'RESERVED'
    AND expires_at <= NOW()
  ORDER BY expires_at, id
  LIMIT 100
  FOR UPDATE SKIP LOCKED;


SKIP LOCKED không thích hợp cho general-purpose consistent reads, nhưng PostgreSQL chính thức
mô tả nó là phù hợp để giảm lock contention khi nhiều consumers truy cập một queue-like table; đó
chính xác là behavior mong muốn của nhiều expiry workers cạnh tranh lấy batch work. 9

         Query/workload                       Index

         Expired reservations                  (status, expires_at)

  # ADR-003: Use Conditional Database Update for Ticket Reservation


  ## Status

  Accepted

  ## Context

  Ticket inventory is finite and concurrent booking attempts can target
  the same ticket category.

  A SELECT-then-UPDATE implementation permits a race where multiple
  transactions observe the same available quantity.

  ## Decision Drivers




                                                   18
- no overselling
- simple failure semantics
- stated load does not require distributed locking
- PostgreSQL is the inventory source of truth


## Options Considered

### Conditional UPDATE
Pros:
- atomic at database boundary
- simple
- no secondary lock service


Cons:
- hot row contention remains possible

### SELECT ... FOR UPDATE
Pros:
- explicit locking and easy reasoning

Cons:
- waiting transactions and longer lock holding if transaction grows

### Redis Distributed Lock
Pros:
- external coordination

Cons:
- adds a second failure/consistency boundary

## Decision

Use conditional UPDATE with available_quantity >= requested_quantity.

## Consequences

Positive:
- inventory cannot be decremented below requested capacity by racing updates
- simple handling based on affected rows

Negative:
- a highly contended category becomes a hot database row
- transaction duration must remain short

## Verification

CONC-001: 100 concurrent requests against inventory=10.
Expected exactly 10 reservations and final available_quantity=0.

Transactional outbox design

Chỉ thêm nếu core booking tests đã hoàn chỉnh.


Problem:



  DB transaction commits
        ↓
  application publishes BookingConfirmed
        ↓
  process crashes before publish

  booking exists
  event disappears


AWS Prescriptive Guidance mô tả transactional outbox chính xác để xử lý dual-write problem này:
domain data và outbox event được ghi trong cùng transaction; publisher riêng đọc committed outbox
và gửi ra broker/downstream system. AWS cũng lưu ý delivery có thể tạo duplicates, nên consumers vẫn
phải idempotent. 21


Schema:




                                                  37
  CREATE TABLE outbox_events (
      id uuid PRIMARY KEY,
      aggregate_type text NOT NULL,
      aggregate_id uuid NOT NULL,
      event_type text NOT NULL,
      payload jsonb NOT NULL,
      created_at timestamptz NOT NULL DEFAULT NOW(),
      published_at timestamptz NULL
  );

  CREATE INDEX idx_outbox_unpublished
  ON outbox_events(created_at)
  WHERE published_at IS NULL;


Transaction:



  BEGIN

  UPDATE bookings
  SET status = 'CONFIRMED'
  ...

  INSERT INTO outbox_events(
     event_type,
     aggregate_id,
     payload
  )
  VALUES (
     'BookingConfirmed',
     ...,
     ...
  );

  COMMIT


Outbox design document nên ghi rõ:



  Implemented:
  Postgres outbox table + polling worker

  Not implemented:
  Kafka / RabbitMQ

  Future:
  replace publisher destination without changing booking transaction

SQL evidence box

Đặt một box kiểu này trong Database Design:



  ## Critical Database Guarantees

  ### Inventory never goes negative

  ```sql




                                                                       43
  UPDATE ticket_inventories
  SET available_quantity = available_quantity - :qty
  WHERE ticket_category_id = :category_id
    AND available_quantity >= :qty
  RETURNING available_quantity;


Guarantee: The write succeeds only while sufficient inventory exists.


Evidence: CONC-001.


Duplicate logical requests


  UNIQUE(user_id, idempotency_key)


Guarantee: Two transactions cannot persist two idempotency records with the same scope/key.


Evidence: CONC-002.


Voucher global quota


  UPDATE vouchers
  SET used_count = used_count + 1
  WHERE id = :voucher_id
    AND used_count < usage_limit
  RETURNING used_count;


Evidence: CONC-003.



  PostgreSQL unique constraints formally guarantee uniqueness over the
  constrained column set, và conditional updates/`RETURNING` cho phép chính
  database write xác định operation có thành công hay không. 26
